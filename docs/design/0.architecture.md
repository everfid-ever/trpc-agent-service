## 1. 设计目标与适用范围

`trpc-agent-service` 是构建在 `trpc-agent-go` 公共 API 之上的服务化运行时，负责多租户控制面、IM 接入、分布式调度、共享数据、治理、审计和部署。`trpc-agent-go` 继续负责 Agent、Runner、Model、Tool 以及 Session/Memory/Artifact 的通用接口。

本方案适用于多租户 IM Agent 的开发、测试和生产部署，重点保证租户隔离、单 Session 串行语义、节点故障接管、消息幂等和全链路可审计。

架构边界如下：

- `trpc-agent-service` 不复制 Agent 框架能力，不 require/import 独立的 `trpc-agent-go/openclaw` 产品模块及其 `runtimeprofile`/Channel 实现。
- `trpc-agent-service` 负责服务级控制面、数据面和运维面能力。
- `trpc-agent-go` 负责通用 Agent 执行抽象及公开的 Session、Memory、Artifact 接口。
- 具体存储厂商和 IM 协议通过稳定端口接入，不进入 Runtime 核心契约。

## 2. 架构原则与组件拓扑

系统遵循以下原则：

1. 可信租户上下文只由服务端认证结果或 Channel Binding 生成。
2. Worker 无状态运行，所有权威状态均位于共享后端。
3. Broker 提供 at-least-once 投递，Inbox、Commit 和 Delivery Ledger 提供效果幂等。
4. Session 互斥依赖 lease 与单调 fence，Broker 分片不承担互斥职责。
5. 跨事务域写入统一使用 Transactional Outbox。
6. 请求进入执行队列后固定 Config、service-owned ExecutionProfile、Policy 和 Backend 版本。
7. 分布式正确性能力缺失时启动失败，不允许静默降级。
8. Governance/Filter Chain 是每个 Worker 内嵌的安全执行边界，对应 Plugin/Guardrail 扩展点和工具权限原语，不是可绕过的独立旁路服务。

| Lease/Fence Coordination | 原子生成 fence，获取、续租和释放 session lease | Redis coordination state | active lease QPS、renew latency |
| Storage Router/Adapter | 强制 tenant scope，选择 Session/Memory/Artifact/Knowledge/Audit 后端 | BackendBinding 与后端权威数据 | backend QPS、连接池和延迟 |
| Admin API | 管理 Tenant、AgentApp、Binding、ConfigSnapshot、灰度和回滚 | PostgreSQL Config Store | 管理请求 QPS；通常独立小规模部署 |
| Audit Relay | 从 Audit Outbox 可靠导出审计事件 | Audit Outbox 和审计后端 | audit lag、export throughput |
| Telemetry Collector | 接收、处理并导出 trace、metric 和 log | 非业务权威状态 | telemetry throughput、queue usage |

## 3. 租户控制面领域模型

控制面至少包含以下领域对象：

```text
Tenant
  tenant_id
  tenant_key / display_name
  status
  request/concurrency quota
  monthly token/cost budget + currency
  audit retention/payload mode + log masking + trace sampling
  default_agent_app_id / default_backend_profile_id
  active_config_version
  version / created_at / updated_at

AgentApp
  tenant_id + agent_app_id
  stable agent_app_key / display_name
  status / current_revision / version

AgentAppRevision
  tenant_id + agent_app_id + revision
  immutable prompt and agent schema
  versioned model/tool/knowledge refs
  content_digest / published_at

ConfigSnapshot
  tenant_id + config_version
  channel/backend/default binding refs
  rollout_state
  immutable_payload_digest

ChannelBinding
  tenant_id + channel + external_account_id
  agent_app_id
  secret_ref
  callback/transport config

BackendBinding
  tenant_id + domain
  backend_type
  backend_ref
  credential_ref
  capability set

Usage/Audit Ledger
  tenant-scoped immutable usage and audit facts
  currency / token / cost_micros
  export and retention execution state
```

tenant 根实体的规范字段、DDL、状态机和复合外键见 [Tenant 根实体与运行时边界技术方案](1.tenant-root-design.md)。根表保持窄，不保存应用、模型、工具、Channel、Backend 参数或 Secret。

Agent App 的执行定义以不可变 Revision 发布，`current_revision` 是新请求的 App 定义指针；ConfigSnapshot 独立承载租户级 Channel、Backend 和默认组合配置。两者不能形成含义重复的版本：运行时 `ExecutionProfileSnapshot` 只是 App Revision、ConfigSnapshot 和 PolicySnapshot 的派生投影，不拥有独立持久版本。完整模型见[控制面领域模型第二部分](1.tenant-root-design.md#第二部分-agent-app-领域模型与发布)。

Revision 和 ConfigSnapshot 激活后都不可原地修改。Agent App 回滚把 `current_revision` 指向历史 published Revision，同时单调递增 App version；Config 回滚把目标历史 payload 复制为新的更大 `config_version` 后再切换 `active_config_version`，不得让配置发布头倒退。`PrepareDispatch` 成功提交的请求继续使用 Envelope 固定的 App Revision、Config 和 Policy 版本。仅完成 ClaimInbox 的消息尚未获得执行资格，必须按最新 tenant/app 状态通过入口门禁。

## 4. 租户上下文与运行标识

三者各自承担不同职责：

- `TenantContext`：由可信入口建立的安全和路由身份，只包含租户、应用、主体和来源；不把尚未解析的运行版本伪装成身份事实。
- `ExecutionBinding`：`PrepareDispatch` 从控制面一致读视图解析出的固定 App Revision、Config 和 Policy 版本。
- `SessionInfo`：一次 Runner/Session 调用使用的 AppName、UserID、SessionID 等运行信息。
- `AppName`：与 `trpc-agent-go` 现有 Session key 兼容且便于运维阅读的应用名，不是租户认证凭据。

`TenantContext` 与 `ExecutionBinding` 的字段、类型和构造边界以[控制面领域模型第一部分 §7.2](1.tenant-root-design.md#72-tenantcontextsessioninfo-与-appname)为唯一权威定义；本节只描述它们在总体架构中的职责与流转关系。

Channel/Gateway 先建立 TenantContext，`PrepareDispatch` 再生成 ExecutionBinding，并将两者共同写入权威 execution record 和 Envelope。Worker 必须从 TaskStore 复核两者，不能接受调用方自行注入的版本绑定。

服务端根据可信 Tenant 和 Agent App 根实体计算 AppName，规范格式为 `tenantSlug/agentAppSlug`。校验必须基于结构化字段与固定 Config/App Revision 精确匹配，不得通过字符串前缀或后缀推导 tenant。客户端提交的 AppName 仅作为可选期望值；与服务端结果不一致时请求被拒绝。

## 5. 用户身份与 Session 标识

内部 session key 始终包含：

```text
tenant_id + agent_app_id + session_id
```

内部 UserID 和 SessionID 使用带版本的 canonical encoding 与确定性 HMAC，避免拼接碰撞和外部 ID 泄露：

```text
User:  HMAC(tenant_identity_key, channel | account | external_user)
DM:    HMAC(tenant_session_key, channel | account | "dm" | external_user)
Group: HMAC(tenant_session_key, channel | account | "group" | external_chat)
```

实现必须使用长度前缀或等价 canonical encoding，不得直接连接可变长字段。详细规则见 [Tenant 根实体第 7.3 节](1.tenant-root-design.md#73-userid-与-sessionid-命名空间)。

同一用户跨群默认形成不同 session；跨租户永远不同。若产品支持跨群连续记忆，只能通过租户策略将独立 session 的内容写入租户作用域 Memory，不能复用 session ID。

## 6. 核心处理链路

核心链路为：`IM → Channel Adapter → Inbox/Preprocess → Gateway → Dispatch Outbox → Broker → Worker → Governance/Filter → Runner → Model/Tool → Session/Memory → CommitTurn → Reply Outbox → Channel Adapter → IM`。规范性端到端时序见第 12 节，关键异常与恢复分支见第 13 节。

## 7. 跨进程执行契约

跨进程只传可序列化、固定版本的事实，不传 Runner、Model、Tool、数据库客户端或密钥。`ExecutionEnvelope` 的字段、类型和演进规则以 [Gateway/Worker §2.1](2.gateway-worker-design.md#21-executionenvelope-权威契约)为唯一权威定义；本节只规定其架构语义。

Worker 必须重新读取指定版本并验证租户、应用、Revision、digest 和能力，不能使用“当前 latest”替代 Envelope 固定版本。`AgentAppRevision` 是 Agent 定义的唯一发布版本；运行时投影不得再维护第二套版本计数。

## 8. 一致性模型与后端基线

- Session head、input 顺序、提交结果和业务 Outbox：强一致/CAS。
- Memory 提炼和向量索引：默认最终一致，支持请求级 read-your-writes overlay。
- Summary：异步生成，但以 `base_session_seq` 单调提交。
- Artifact：对象本身可最终一致，元数据和租户授权必须强一致。
- Audit：业务提交时写 Audit Outbox，异步导出且可重放。

基线部署采用 PostgreSQL 作为权威事务存储、Redis Streams 作为 Broker、Redis 作为 lease/fence 协调后端。SQL 与 Redis 属于不同事务域，因此派发和回复统一经过 Outbox。

## 9. Worker 无状态模型

Worker 进程内只允许保存可失效、可重建的数据：

- 带版本的配置和 ExecutionProfile 缓存；
- 模型/后端客户端连接池；
- 当前执行 goroutine 和续租器；
- 指标聚合缓冲。

权威 Session、Memory、执行状态、确认状态和回复游标必须共享持久化。节点失效后由 lease 过期、Broker 重投和 fence 拒绝旧 owner 完成接管，因此不需要 sticky session。

## 10. 租户隔离与安全边界

- 所有请求在 Adapter/Gateway 和 Worker 两次验证 TenantContext 与固定快照。
- Storage Adapter 无条件追加 tenant scope，不允许调用者传入未限定查询。
- 工具列表按 PolicySnapshot 构造；工具隐藏与授权必须由运行时强制执行，不得依赖模型提示词。
- Channel、Worker 和 Admin API 使用不同工作负载身份及最小 Secret 权限。
- payload、模型内容、工具参数和外部用户 ID 按数据等级脱敏。
- 租户停用、密钥撤销和危险策略变更必须 fail closed。

## 11. 进程与部署形态

同一二进制提供多个角色：

```text
trpc-service all
trpc-service gateway
trpc-service worker
trpc-service relay --kind=dispatch|reply|wakeup|tenant-control
trpc-service channel --provider=telegram|wecom
trpc-service preprocess
trpc-service audit-relay
trpc-service admin
trpc-service migrate
```

本地开发可由 `all` 合并启动；生产环境按角色独立扩缩和授权。

### 12.1 交互阶段划分

| 阶段 | 交互编号 | 责任模块 | 阶段完成条件 |
|---|---:|---|---|
| 配置发布 | 1–6 | B、C、D、Admin API | App Revision 或 ConfigSnapshot 不可变持久化，指针、审计和失效 Outbox 原子提交 |
| IM 接入与幂等 | 7–15 | B、C | 外部消息完成协议校验与 ClaimInbox；重复消息返回既有结果，新消息获得 durable ACK |
| 请求标准化与派发 | 16–22 | A、B、C | 固定执行版本，生成 execution record，并通过 Dispatch Outbox 可靠发布 |
| Worker 调度与所有权 | 23–30 | A、B | Worker 完成 Envelope 复核、lease/fence 获取、input gate 或故障接管 |
| 治理与 Agent 执行 | 31–51 | A、B、C、D | 固定策略完成决策；允许路径显式完成 Session/Memory 读取、Model/Tool 调用、CommitTurn 和 Memory 可见性 |
| 执行收尾 | 52–56 | A、B | Broker delivery 已 ACK，lease 安全释放，ReplyEvent 写入持久回复流 |
| IM 回复与观测闭环 | 57–61 | C、D | 回复完成脱敏、分片和幂等投递，审计可查询，Trace 闭合 |

### 12.2 核心时序约束

- 交互 10 成功是外部消息可靠接收的边界。未完成 ClaimInbox 时不得向 IM 平台返回成功 ACK。
- 重复消息执行交互 12–13；新消息执行交互 14–61。二者共享同一个外部消息幂等键。
- 交互 19–22 采用 Transactional Outbox：B 在 PostgreSQL 事务内保存 execution record 与 Dispatch Outbox，A 的 Relay 负责发布 Broker。
- 交互 24–25 包含 `input_seq < next`、`input_seq == next`、`input_seq > next` 三态门禁。
- 交互 26–28 表示故障接管，交互 29–30 表示正常续租；两条分支均不得绕过持久化 fence 校验。
- 交互 34–35 表示拒绝或等待确认，交互 36–51 表示允许执行。终态推进 `next_input_seq`，`waiting_confirmation` 不推进。
- 交互 48–49 必须以 CommitTurn 原子提交 Session event、state、terminal、`next_input_seq`、Memory durable intent 和业务 Outbox。
- 交互 50 的 Memory 写入允许跨后端最终一致，但必须由已提交 intent 重试，并通过 version/失效通知实现跨节点可见。
- 交互 54–61 仅负责回复投递和观测，不得重新触发 Agent 执行。

## 13. 关键分支交互时序

本节展开主时序中的重复投递、并发竞争、外部依赖故障和恢复分支。组件内部字段、状态转换和错误分类以对应模块设计为准。

### 13.1 IM 消息接入、租户解析与预处理

```mermaid
sequenceDiagram
  autonumber
  participant IM as Telegram or WeCom
  participant C as C Channel Adapter
  participant B as B Binding and Inbox Store
  participant P as C Preprocess Worker
  participant G as A Gateway
  participant RC as Reconciler

  IM->>C: Callback frame or update
  C->>C: Verify decrypt and normalize
  C->>B: Resolve Binding and trusted tenant
  C->>C: Map user and derive DM or group session
  C->>B: ClaimInbox external key digest and payload ref
  alt Inbox database unavailable
    B--xC: Retryable error
    C-->>IM: Retryable platform response
    Note over C,IM: No durable claim means no success ACK
  else First delivery
    B-->>C: New stable request ID and pending state
    C-->>IM: ACK after durable claim
  else Duplicate delivery
    B-->>C: Existing request ID and state
    C-->>IM: ACK without a second request
  end
  opt Media scan or input DLP is required
    C->>B: Create preprocess job
    P->>B: Claim job lease
    P->>P: Download validate scan and classify
    alt Temporary failure
      P->>B: CAS retry wait and not before
    else Input rejected
      P->>B: Mark Inbox rejected and write Audit Outbox
      Note over B,G: No input seq is allocated
    else Input ready
      P->>B: Save sanitized payload and mark ready
      P->>G: Dispatch ready request
    end
  end
  opt Adapter crashes after ACK
    C-xC: Process stops before dispatch
    RC->>B: Scan pending or ready Inbox
    RC->>G: Resume dispatch with stable request ID
  end
```

设计约束：TenantContext 来自 Binding；ClaimInbox 原子保存 request ID 和 payload ref；重复回调、Adapter 崩溃和预处理重试不得重复运行 Agent。

### 13.2 请求派发、Worker 调度与故障接管

```mermaid
sequenceDiagram
  autonumber
  participant G as A Gateway
  participant B as B Atomic Store
  participant DR as A Dispatch Relay
  participant Q as Redis Streams
  participant W1 as Worker 1
  participant L as Lease and Fence Store
  participant R as Runner
  participant W2 as Worker 2

  G->>B: PrepareDispatch transaction
  B->>B: Allocate input seq freeze versions write Outbox
  DR->>B: Claim Dispatch Outbox
  DR->>Q: Publish idempotent Envelope
  alt Broker unavailable
    Q--xDR: Publish failed
    DR->>B: Mark retry and release claim
    DR->>Q: Retry after backoff
  end
  Q->>W1: Deliver at least once
  W1->>B: Revalidate trusted request and versions
  W1->>L: Acquire session lease
  L-->>W1: Lease L1 and fence 41
  W1->>B: OpenForRun
  alt input seq is lower than next
    B-->>W1: AlreadyTerminal with CommitResult
    W1->>Q: ACK without Runner
  else input seq is greater than next
    W1->>B: Persist parked input and release lease
    W1->>Q: ACK and wait for Wakeup Outbox
  else input seq equals next
    W1->>R: Run with tenant scoped services
    R-->>W1: Events state usage and reply
    opt Durable cancel arrives
      G->>B: CAS cancel intent
      W1->>R: Cancel local context before commit
    end
    alt Lease remains valid
      W1->>B: CommitTurn fence 41
      B->>B: Atomic event state terminal next and Outboxes
      alt Worker crashes before Broker ACK
        W1-xW1: Process stops
        Q->>W2: Reclaim same delivery
        B-->>W2: AlreadyTerminal with CommitResult
        W2->>Q: ACK without Runner
      else Worker remains healthy
        W1->>Q: ACK committed delivery
      end
    else Lease renewal is lost
      L->>L: L1 expires
      Q->>W2: Reclaim delivery
      L-->>W2: New lease and fence 42
      W2->>B: Execute and CommitTurn fence 42
      W1->>B: Late CommitTurn fence 41
      B-->>W1: ErrStaleFence
    end
  end
```

设计约束：分片不代替 lease；较大 input 被 park 而不空转；SQL 与 Redis 之间通过 Outbox 协作；旧 Worker、重投和 ACK 丢失均不得产生第二次业务效果。

### 13.3 运行时治理、模型工具调用与危险操作确认

```mermaid
sequenceDiagram
  autonumber
  participant W as A Worker
  participant C as C Governance
  participant B as B Atomic Store
  participant R as Runner
  participant M as Model Provider
  participant T as Tool Provider
  participant IM as IM Platform
  participant W2 as Any Worker

  W->>C: Evaluate fixed policy subject budget and model
  alt Policy denies
    W->>B: Commit denied terminal and advance next
  else Policy allows
    W->>R: Run with visible tool set
    R->>M: Generate with logical request key
    alt Model timeout and retry allowed
      R->>M: Bounded retry
    else Model timeout and retry forbidden
      R-->>W: Failed or configured fallback
    else Model succeeds
      M-->>R: Tool call or response
    end
    opt Model requests a tool
      R->>C: Check actual args resource and budget
      alt Tool denied
        C-->>R: Deny result and audit
      else Tool allowed
        R->>T: Execute with idempotency key
        alt Result is ambiguous
          T--xR: Response lost after possible effect
          R->>B: Persist ambiguous outcome
          R->>T: Query result or suspend safely
        else Tool succeeds
          T-->>R: Tool result
        end
      else Dangerous tool asks for confirmation
        C-->>R: SuspensionRequest
        R-->>W: Stop event loop and checkpoint
        W->>B: Commit waiting and release lease
        B-->>IM: Send confirmation prompt
        IM->>C: Approve deny or duplicate callback
        C->>B: CAS decision
        alt Denied or expired
          B->>B: Commit terminal and advance next
        else Approved
          B->>B: Create one time grant and continuation
          W2->>B: Acquire new fence and consume grant
          W2->>R: Resume same request input and checkpoint
          W2->>B: Commit terminal and advance next
        end
      end
    end
  end
```

设计约束：工具同时实施可见性与执行前授权；waiting 状态不推进 next；grant 只能消费一次；有副作用工具的模糊结果不得盲目重放。

### 13.4 回复发布、IM 投递与 Channel 节点接管

```mermaid
sequenceDiagram
  autonumber
  participant B as B Outbox and Delivery Store
  participant RR1 as Reply Relay 1
  participant Q as Account Reply Queue
  participant RR2 as Reply Relay 2
  participant C1 as Channel Adapter 1
  participant L as Connection Lease Store
  participant IM as Telegram or WeCom API
  participant C2 as Channel Adapter 2

  RR1->>B: Claim Reply Outbox E
  RR1->>Q: Publish delivery key D
  alt Relay crashes before mark
    RR1-xRR1: Process stops
    B->>B: Claim lease expires
    RR2->>Q: Republish the same D
    RR2->>B: Mark published
  else Relay remains healthy
    RR1->>B: Mark published
  end
  C1->>L: Acquire account connection lease if required
  Q->>C1: Deliver ReplyEvent one or more times
  C1->>C1: Render capabilities and split segments
  loop Each unsent segment
    C1->>B: Claim delivery key and segment
    C1->>IM: Send edit card media or text
    alt Success
      C1->>B: Mark segment sent
    else Rate limited
      IM-->>C1: 429 and retry after
      C1->>B: Mark retry wait
    else Response is lost
      C1->>B: Mark ambiguous for reconciliation
    end
  end
  opt Adapter owner fails
    C1-xIM: Connection lost
    L->>L: connection lease expires
    C2->>L: Acquire account lease
    C2->>Q: Claim pending deliveries
    C2->>B: Resume from first non sent segment
    C2->>IM: Continue delivery
  end
```

设计约束：回复权威状态位于共享 Outbox、队列和 Delivery Ledger；已确认分片不得重发；Channel 节点故障不得绑定 Session 或触发 Agent 重跑。

### 13.5 配置发布、派生数据一致性与后端迁移

```mermaid
sequenceDiagram
  autonumber
  participant A as Admin API
  participant B as B Config and Data Store
  participant W1 as Worker 1
  participant W2 as Worker 2
  participant V as Invalidation Stream
  participant M as Migration Coordinator
  participant S as Source Backend
  participant T as Target Backend

  A->>B: Activate immutable config version 12 for canary
  B-->>W1: New Envelope fixes version 12
  A->>B: Roll back using version 11 payload
  B->>B: Publish copied payload as new version 13
  B-->>W1: In flight request still resolves version 12
  B-->>W2: New request resolves version 13 equivalent to 11
  W1->>B: Persist Memory version 31
  B->>V: Publish invalidation version 31
  V-->>W2: Invalidate tenant cache
  W2->>B: Read version at least 31
  par Older summary runs slowly
    W1->>B: Submit summary base seq 10
  and Newer summary finishes first
    W2->>B: CAS summary base seq 20
  end
  W1->>B: CAS summary base seq 10
  B-->>W1: Reject stale summary
  A->>M: Start tenant backend migration
  M->>S: Capture checkpoint and snapshot
  loop Backfill stable batches
    M->>S: Read IDs and source versions
    M->>T: Idempotent upsert mutation IDs
    M->>M: Save checkpoint
  end
  M->>M: Enable durable dual write and repair
  M->>S: Verify count digest and watermark
  M->>T: Verify count digest and watermark
  M->>B: Activate config version reading target
  Note over S,T: Keep rollback sync through observation window
```

设计约束：在途请求使用固定配置；Memory 通过版本检查修复通知丢失；Summary 水位单调；迁移必须具备 checkpoint、幂等双写、对账和回滚窗口。

### 13.6 节点摘流、可观测降级与审计恢复

```mermaid
sequenceDiagram
  autonumber
  participant K as Kubernetes
  participant W1 as Draining Worker
  participant Q as Broker
  participant L as Lease Store
  participant B as B Business and Audit Store
  participant W2 as Healthy Worker
  participant O as D OTel SDK and Collector
  participant AR as D Audit Relay
  participant AS as Audit Backend

  K->>W1: SIGTERM
  W1->>W1: Readiness false and stop new consume
  alt Turn completes before deadline
    W1->>B: Commit result and Audit Outbox
    W1->>Q: ACK delivery
    W1->>L: Release lease
  else Drain deadline expires
    W1->>W1: Cancel work and stop renewal
    L->>L: Lease expires
    Q->>W2: Reclaim delivery
    L-->>W2: New lease and larger fence
    W2->>B: Execute and CommitTurn
  end
  W2->>O: Export spans metrics and logs
  alt Collector unavailable
    O->>O: Bounded buffer then drop noncritical telemetry
    Note over W2,O: Business remains available
  end
  AR->>B: Claim durable Audit Outbox
  AR->>AS: Export AuditEvent
  alt Audit Backend unavailable
    AS--xAR: Export failed
    AR->>B: Mark retry and retain Outbox
  else Export succeeds
    AR->>B: Mark audit published
  end
```

设计约束：Drain 先摘流，超时后由新 fence 接管；Telemetry 允许有界降级，审计意图必须保存在可重放的 Audit Outbox。
